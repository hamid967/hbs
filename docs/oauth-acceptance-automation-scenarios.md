# سيناريوهات اختبار آلية لقبول OAuth

**النطاق:** تحقق آلي خادمي لمسار الموافقات، توجيه الوحدات، عزل الشركة، والصلاحيات. لا تحاكي هذه الاختبارات تسجيل دخول OAuth حقيقياً ولا تنشئ حسابات أو جلسات بديلة؛ لذلك تبقى جلسات الموظف والمدير والوحدة المختصة الفعلية شرطاً منفصلاً للقبول الحي.

| المعرف | السيناريو الآلي | ملف الاختبار | معيار النجاح |
|---|---|---|---|
| AUTO-01 | إنشاء طلب داخل الشركة وتعيين المدير المباشر | `server/approvalWorkflow.integration.test.ts` | تنشأ مهمة المدير وسجل المرحلة داخل الشركة نفسها. |
| AUTO-02 | انتقال طلب HR بعد قرار المدير | `server/approvalWorkflow.integration.test.ts` و`server/approvalRouting.test.ts` | تنشأ مهمة HR وإشعار الوحدة الصحيحة فقط. |
| AUTO-03 | انتقال طلب العلاقات الحكومية بعد قرار المدير | `server/approvalWorkflow.integration.test.ts` و`server/approvalRouting.test.ts` | تنشأ مهمة العلاقات الحكومية وإشعار الوحدة المطابقة فقط. |
| AUTO-04 | القرار النهائي للوحدة وإشعار الموظف | `server/approvalWorkflow.integration.test.ts` | يستلم الموظف وحده إشعار القرار النهائي. |
| AUTO-05 | منع قرار المرحلة الثانية قبل قرار المدير | `server/approvalWorkflow.integration.test.ts` | يرفض الإجراء ولا ينشئ سجلات أو تحديثات. |
| AUTO-06 | عزل صندوق الموافقات حسب الدور والحساب | `server/routers/approvals.test.ts` | يرى المدير أو HR أو العلاقات الحكومية صندوقه المخول فقط. |
| AUTO-07 | منع الحساب غير المخول من قرار الموافقة | `server/routers/approvals.test.ts` | يعيد الإجراء `FORBIDDEN` ولا تصل الدعوة إلى طبقة البيانات. |
| AUTO-08 | جاهزية الأدوار والارتباطات دون كشف هويات | `server/oauthAcceptanceReadiness.test.ts` و`server/_core/systemRouter.test.ts` | تعرض المؤشرات المجمعة للمسؤول فقط ولا تتضمن معرفات مستخدمين. |

## أوامر التشغيل

```bash
pnpm vitest run \
  server/approvalWorkflow.integration.test.ts \
  server/approvalRouting.test.ts \
  server/routers/approvals.test.ts \
  server/oauthAcceptanceReadiness.test.ts \
  server/_core/systemRouter.test.ts

pnpm check
pnpm test
```

## ما يبقى للقبول الحي

| السيناريو الحي | لماذا لا تؤتمت هذه الحزمة؟ | الدليل المطلوب |
|---|---|---|
| دخول الأدوار الثلاثة عبر OAuth | يتطلب جلسات OAuth فعلية مستقلة وحالة تفعيل حقيقية. | محضر جلسة ودور وبيئة وإصدار. |
| ظهور الإشعارات في واجهات المستخدم الفعلية | يعتمد على الجلسات الحية وتسليم الواجهة النهائي. | لقطات أو سجل زمني من كل جلسة. |
| خصوصية الملاحظات من منظور الموظف | يحتاج فحص الواجهة في جلسة الموظف الفعلية. | تحقق أن الحالة والتاريخ ظاهران من دون ملاحظات مراجعين. |
| الربط بالإصدار المنشور | يعتمد على بيئة القبول أو الإنتاج ورقم البناء الظاهر. | تسجيل الإصدار والالتزام قبل بدء السيناريو. |

> لا تتحول مراحل القبول الحي إلى مكتملة إلا عند نجاح السيناريوهات الفعلية الواردة في `docs/oauth-live-acceptance-execution-checklist.md` وتوثيقها من الأدوار المستقلة.

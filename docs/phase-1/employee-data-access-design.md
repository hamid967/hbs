# تصميم حماية بيانات ملف الموظف

## القرار التنفيذي

تتبع دفعة خصوصية ملف الموظف مبدأ **المنع الافتراضي**: لا تكفي هوية المستخدم أو ظهور عنصر في الواجهة للوصول إلى ملف موظف أو حقل حساس. يقرر الخادم على كل طلب ما إذا كان الدور والعلاقة مع السجل ونطاق الشركة يسمحان بالقراءة أو التعديل. تُعرض للمشرف المباشر البيانات التشغيلية اللازمة للمتابعة فقط، ولا يعاد له رقم الموظف أو تاريخ الانضمام أو البريد أو معرّف OAuth ضمن استجابة الدليل.

> «Permission should be validated correctly on every request… an attacker only needs to find one way in.» — OWASP Authorization Cheat Sheet [1]

| القرار | التطبيق في المنصة |
|---|---|
| أقل قدر من الوصول | يستمر المدير في رؤية نفسه ومرؤوسيه المباشرين فقط، مع حذف الحقول الحساسة من شكل الاستجابة نفسه. |
| تفويض على مستوى الكائن | يتحقق `canReadEmployee` و`canUpdateEmployee` من `companyId` ومعرّف الموظف وعلاقة المدير المباشر. |
| عدم كشف المعرّفات | لا يعيد مسار الدليل البريد أو `openId`، وتبقى عمليات التعديل محمية بتحميل مرجع موظف محكوم بالشركة. |
| عدم افتراض الالتزام | لا تضيف هذه الدفعة أرقام هوية وطنية أو تفاصيل تعويض أو ادعاءات امتثال تنظيمي. |

يشرح مبدأ أقل قدر من الوصول أن على المستخدم أو العملية الحصول فقط على الصلاحيات اللازمة لوظيفته، للحد من مساحة الهجوم وأثر أي اختراق [2]. لذلك لا تضيف الدفعة حقول بيانات شخصية جديدة، وتتعامل مع حقول الملف الموجودة فعلاً كبيانات تحتاج إلى عرض محدود بحسب الدور والسياق.

## حدود الدفعة

لا تشفر هذه الدفعة حقولاً جديدة، ولا تغير مفاتيح تخزين أو جلسات OAuth، ولا تطبق ترحيلاً لقاعدة البيانات. وهي لا تعد بامتثال قانوني أو تنظيمي؛ المراجعة القانونية ومتطلبات الاحتفاظ بالبيانات وتعيين ملاك الخصوصية مسار حوكمة مستقل.
